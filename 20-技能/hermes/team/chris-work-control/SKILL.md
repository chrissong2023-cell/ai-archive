# 工作总控（Chris 的任务台账与汇报节奏）

## When to Use

- 要记任务、改任务状态、查待办（包括"我有点凌乱，帮我规划"这类请求）。
- 要发每日 08:00 / 20:00 工作汇报。
- 要定一条规则、改一条规则（决策记录）。
- 处理任何属于 Chris 的业务事项之前——先看台账里有没有已经在跑的同一条。

## 一、唯一真相：tasks.jsonl

```
~/AI工作台/00-总控/
├── tasks.jsonl          ← 任务唯一真相（不要手改 TASKS.md，它是生成物）
├── bin/ctl.py           ← add | list | done | start | block | reopen | digest | ledger | projects
├── DECISIONS.md         ← 追加式决策记录（最新在最上面）
├── DAILY/YYYY-MM-DD.md  ← 每日汇总
├── OUTBOX/              ← 待发邮件与急件草稿（发前写这里）
├── 角色定位/            ← Chris 交付的长期工作准则（六份）
├── 规划/                ← 90 天作战计划、每日节奏单页、专题规划
└── STATE/ · LEDGER.jsonl← 邮件事实/指令流水
```

```bash
python3 ~/AI工作台/00-总控/bin/ctl.py list
python3 ~/AI工作台/00-总控/bin/ctl.py add "标题" --project 客户开发 --owner chris [--due 2026-11-01] [--approve]
python3 ~/AI工作台/00-总控/bin/ctl.py start <id> | done <id> --note "…" | block <id> --note "…"
python3 ~/AI工作台/00-总控/bin/ctl.py digest      # 重建 TASKS.md
```

规则：
1. **聊天里答应的进展不算数**；写进 `tasks.jsonl` 才算。口头新增/关闭任务后立刻用 `ctl.py` 落一条。
2. 需要 Chris 点头才能执行的标 `approve`；这类任务堆在他那边，是他"凌乱"的主因——汇报时单独列一行"待你批"。
3. 逾期任务（`due` 早于今天且未关闭）在汇报里必须点名，别埋在列表里。
4. 一个事项只登记一次；同一件事第二次出现时先 `list` 查重，避免两套并行。

## 二、决策记录（DECISIONS.md）

每条决策写清：谁定的 / 何时 / 依据（尽量带原话）/ 影响面。不删旧记录；被推翻时新增一条并注明"取代 X"。

**写入坑（踩过两次）**：文件是"最新在最上面"，用 find-replace 插在某个 `## 标题` 之前时，若把该标题写进 `old_string` 又忘了在 `new_string` 里带回来，**下面那条记录的标题会被吃掉**，正文变成孤立的 bullet。正确做法：`old_string` 与 `new_string` 都从**下一个标题那一行**开始/结束，写完立刻回读前 20 行确认标题齐全。

## 三、角色定位（六份长期准则）

`00-总控/角色定位/` 下六份，属于"每次会话都生效"的输出标准：

| 文件 | 管什么 | 输出格式 |
|---|---|---|
| 01-私人战略顾问与企业经营总顾问 | 战略/商业模式/业务选择/决策支持 | 8 段式 |
| 02-个人成长学习与生活管理教练 | 学习/时间/网球/睡眠/语言 | 按需 6 段式 |
| 03-Nova2.0个人AI系统架构师 | 跨系统设计/自动化/工具引入 | 架构图+七要素+七步实施 |
| 04-投资研究与资产配置顾问 | 投资/配置/风险 | 9 段式 |
| 05-国际物流国际贸易与供应链商业顾问 | 客户开发/方案/报价结构 | 9 段式 |
| 06-AI算力GPU服务器与IDC商业顾问 | GPU/IDC 项目测算与核实 | 10 段式 |

各段式的具体条目见 `references/answer-formats.md`（要照着写时读它）。

两条跨领域硬规矩（Chris 明确要求，适用于全部六份）：
- **不许一味附和**：发现逻辑错误、风险、不合理假设，直接指出。
- **方案必须带成本口径**（毛利、资金占用、周期）；只谈收入的方案视为不合格。

## 四、每日汇报（08:00 / 20:00）

```bash
python3 ~/.hermes/scripts/daily_progress.py     # 只读快照：任务/邮件/定时任务/项目/投喂/今日产出
```

两条 cron 把它交给 LLM 润色后发微信：`每日早报·工作汇报0800`、`每日晚报·工作汇报2000`（`--script daily_progress.py`，`--deliver weixin:<home chat>`）。改汇报口径改这两条 job 的 prompt，不要改脚本的输出结构（脚本是数据层）。

**汇报格式（微信）**：纯文本，不用 Markdown 表格/反引号/代码块；先给"今天要做的 3 件事"（从逾期与待批里挑），再给昨日进展；每条带证据（文件路径/任务号）；末尾一行"需要你 1 句话的：…"；总长控制在手机两屏内。

## 五、每日节奏（对外承诺，别自己加码）

`00-总控/规划/每日节奏-单页.md`：Chris 每天只批一次决策（08:00 窗口），12:00 / 18:00 各 10 分钟批邮件草稿，周五 17:00 看钱。**窗口之外不拿执行细节打扰他**（钱、印章、合规例外）。安排他的时间时，永远先问"这是不是该进窗口"。

## 六、常见坑

- **别手改 `TASKS.md`**：它是 `ctl.py digest` 的生成物，改了会被覆盖。
- **别把"待 Chris 批"埋在长文里**：单独列清单，带任务号，一次不超过 6 条。
- **汇报别复述过程**：他要知道的是"完成了什么/卡在哪/下一步一件"，不是你的工具调用史。
- **规划不要重复造**：`规划/2026-Q4-90天作战计划.md` 已存在；他再说"帮我做个规划"时，先读它，补缺口而不新开一份。
- 写规划时把**他必须亲自做的事**（定价、签约、付款、印章、许可判断）与**系统能做的**分开列，否则他永远被拉回执行层。
